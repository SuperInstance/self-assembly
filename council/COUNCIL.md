# ROUND 1

## The Mechanic — opening statement

### Opening case

Three ideas in my design that survive contact with the enemy:

**1. The invariant is enforced by a token boundary, not by good behavior.** "Fetched code never runs in a job that can mint a vault token or push to the repo." The bench job holds `contents: read`, no `id-token`, no secrets — GitHub's own permission model is the enforcer, and the model cannot negotiate with it. A hash pin proves the bytes are the same as tested, never that they're safe, so isolation does the safety work. The growth rule, the gate grammar, even my own prose — all courtesy. The split is the machine.

**2. Probes rerun on every use, so three mechanisms get deleted, not designed.** Because every bench dispatch re-runs `probe/*.sh` first, there is no updater (an update is an edited pin), no repair path (a failed use re-enters the build loop), and no hardware compatibility table (a changed body fails probes and triggers repair). Registration isn't a ceremony, it's a directory move; "verified" is a rerunnable fact, never an agent-written claim. The design is smaller *because* the enforcement is real.

**3. Judges grow bottom-up, from failed rules, with a pre-written deletion condition.** A judge exists only where a rule was tried and failed; the failing probe is its first case; every case carries `{facts, answer, why, origin}` and replays. And the exit is built in: "if the gunner later finds a rule that reproduces every case, delete the judge." I also named the wounds honestly in residual risks — the `run_shell` hole, untrusted operator output, URL rot — because a design that tells you where it bleeds is one you can reason about. That honesty *is* the armor.

### Attacks

**Vs. Kimi (the adversarialist).** I quote their own stress test: *"Attack the dual-source verification with a typosquatted second URL in a proposal and see if the proposal path files an issue or installs. That's the seam where everything else holds or breaks."* By their own admission, the entire trust model rests on a step where the proposer — an LLM reading untrusted web text — *selects the evidence*. Verification against attacker-chosen evidence is not verification; it's a verification costume. Whoever writes the proposal picks the second source, and both sources can serve the same hostile bytes. My design removes the choice: the gate enforces a fixed `gh:` release grammar plus a sha256, in a job with no secrets and no write rights, from a script a human installed inline. The evidence is not selected. It's parsed.

**Vs. MiniMax-pragmatic (the builder).** I quote: *"The agent does NOT auto-install in v1. The loop is **propose → approve → build → register**, and the human gate is a feature, not a placeholder."* The gate is a bottleneck for every honest growth decision — the system self-assembles only when a human is awake and clicking — yet simultaneously permeable: the fast path lets the agent itself decide what counts as "read-only" and whether a URL matches a glob, then fetch and execute. And execute *where*? Their own debt section confesses: *"a malicious or buggy plugin runs with the runner's full user privileges. The mitigation is provenance (allowlist + hashes) and review, not isolation."* So fetched code runs in the job holding the credentials anyway — the exact shape my invariant forbids. A gate that stops the honest path and waves through the dangerous one is a tollbooth, not a boundary.

**Vs. MiniMax-distilled (the distiller).** I quote: *"That's achievable by *cutting the network from the shell the installer runs in* plus a fetch recipe that never sees secrets — not by raising a second CI organism that needs feeding, versioning, and its own human-installed bootstrap."* A network flag is a configuration, not a boundary — one undone setting, one runner update, one injected instruction away from silent reopening, enforced by nothing but the fixed core's own discipline. They ask "where do secrets live," then keep the secrets and the fetched code in the same room with the door locked by a setting the room's occupant configures. My split answers their question literally: secrets live in the think job; fetched code runs in the bench job; they never share a room. And one loose end they never tie: the assembler is "hash-checked at every wake" — checked *by whom*? If the agent checks its own assembler, that is self-certification, the tautology their own critique named elsewhere.

**Vs. ZAI (the skeptic).** I quote: *"Grown judges are self-modification laundered past their own law."* Laundering hides the money; my judges arrive with a paper trail and a pre-written destruction order. A judge exists only where a rule was tried and failed; the failing probe is its first case; cases replay; and the exit condition is explicit: *"if the gunner later finds a rule that reproduces every case, delete the judge."* Their Goodhart story needs judges reinforced by success counts — mine accumulate *failures*, each case tagged with `origin`, and the removal clause is the budget law their own critique says is missing. A failing test promoted into a specification, with deletion when a rule reproduces it, is not evasion of "never modify own workflows" — it is judgment converted into the most reviewable artifact there is: a diff the human installed the machinery to produce.

## The Adversarialist — opening statement

### Opening case

**1. "The assembler is never grown" — one invariant that makes the design falsifiable.**
Every failure mode in my table reduces to a single question: *can a plugin reach something outside `plugins/`?* If no, you're safe; if yes, nothing else matters. That's not a slogan, it's a test you can run. I even handed the council the weapon: "Attack the dual-source verification with a typosquatted second URL in a proposal and see if the proposal path files an issue or installs. That's the seam where everything else holds or breaks." An unattacked design is an unfinished one — so I built the attack target into the design and named it.

**2. Dual-source verification answers the bootstrap pinning problem — the problem nobody else names.**
Who verifies the verifier's first input? An agent that can invent a hash and install it has no provenance story at all. My rule: a hash counts as verified only if it appears at two *independent* URLs the assembler fetched itself — or was approved in a signed task / human issue comment. Mismatch or no second source → issue, halt. The critic will call the mirrors correlated; the independence requirement is the mechanism, and it's written down precisely so correlated mirrors fail it.

**3. Judges grown from build feedback, with the anti-Goodhart machinery built in.**
Inner agents are never designed up front — a decision point marked *judgment* twice during test iterations earns a `decision_point` entry, narrower grants than the parent, verdict JSON with a required reason citing a checkable file or probe number (the core spot-checks the citation), confidence < 0.5 escalates to a human, and a judge overridden more than 3× without justification triggers a review issue automatically. `veto: inner` marks safety-relevant ops where the parent may never overrule — only a human issue comment unblocks. Permissive drift doesn't get "beautifully recorded in git"; it gets flagged, reviewed, and re-grown.

### Attacks

**Against Claude Opus (the mechanic):**
> "**`run_shell` hole**: it still executes arbitrary code next to the vault token, and the growth rule only discourages that at prompt level. The real fix is cutting its network or moving it to bench."

The design's headline invariant is "**Fetched code never runs in a job that can mint a vault token or push to the repo**" — and then its own residual risks confess the gunner, the think job that holds vault and push rights, has `run_shell` executing arbitrary code next to the vault token, restrained by one fixed prompt paragraph telling the model not to. A cathedral of isolation for fetched code, and the fox with the token gets a strongly-worded paragraph. Isolation that depends on the model choosing to use it is not isolation — the doc even says so about the Docker alternative ("I would not take it, because isolation would then depend on the model choosing to use the sandbox") while leaving the identical dependence one workflow over. The weakest point of any security design is the threat it lists in its own appendix and ships anyway.

**Against MiniMax pragmatic (the builder):**
> "**Fast path:** source matches `allowlisted_sources` AND the operation is read-only (probe/transcode/summarize — declared in the proposal). The agent may proceed on the next wake without asking."

The human gate is declared "load-bearing" — and then the agent is handed a self-service bypass: it *declares its own operation read-only* in the proposal to take the fast path. The classifier granting exemption from review is the same LLM that benefits from the exemption, and the trust root it's matching against is a glob: `"https://github.com/*"`. Any attacker repo on github.com matches the allowlist. So the confused deputy the skeptic fears doesn't even need an issue comment — it needs the LLM to write "read-only" in a proposal field, which is the entire deputy skill set. The builder's gate is graded by the student walking through it.

**Against MiniMax distilled (the distiller):**
> "a hash counts only if the assembler fetched it from somewhere the agent didn't write."

This sentence is offered as the replacement for dual-source — "Dual-source verification is this sentence wearing a uniform." But the sentence does not exclude agent-chosen sources at all. The agent writes the proposal naming the URL; it didn't write the bytes at that URL. A typosquatted mirror, a compromised CDN, a fresh attacker repo — every one of them satisfies "the assembler fetched it from somewhere the agent didn't write." The uniform isn't empty decoration; it's the *independence* criterion — two agreeing sources, fetched by the assembler, or signed human approval — that turns "fetched somewhere" into "verified." Distillation kept the verb and deleted the adjective that does the work. A receipt that can't distinguish the merchant from the pickpocket is just a souvenir.

**Against ZAI (the skeptic):**
> "**"Judges at runtime decision points."** Collapse to two categories: reversible (no judge — this is the property a git-native system should exploit, since revert exists) and irreversible (human gate)."

The skeptic cross-examined this design's revert story and won: "a wake that dies between "act" and "commit" leaves the world changed and git ignorant, so the next wake repeats it." Comments posted, API calls spent, messages sent, tokens burned — none of these are reverted by `git revert`. The world is not git. Yet the recommendation's "reversible" category is built entirely on the alibi the skeptic just disproved: that revert exists for what the agent touches. A reversible op with no judge is just an unjudged op wearing a lab coat — the same confused deputy, now with a category label instead of a check. The skeptic proved the ground can't hold the foundation, then built on it anyway.

## The Builder — opening statement

### Opening case

**1. Ephemerality deletes half the design space.** The agent dies every 15 minutes and is reborn from git. That one fact kills hot-reload (next wake picks it up), the upgrade protocol (reinstall = a new commit), the uninstaller (`git revert`), and the plugin daemon. The plugin system is a directory, a receipt file, and ~200 lines of loader and needs-handling. Total. Everything else is ceremony we don't need — and ceremony is the enemy, because every mechanism must earn its place by *shipping this week*. A design that can't ship this week is a wish.

**2. TESTS.md is the gate, not vibes.** "An operator that can't pass its own tests never registers. This is the quality gate the whole system rests on." The driver is allowed to be LLM-written and wrong in boring ways, because the *tests* are the product and the agent must pass them before a commit lands. If the tests are weak, the operator is weak — review the tests, not the driver. That single rule does the work of audit trails, argument-taxonomy passes, and dual-runner verification combined.

**3. The human gate is a feature, not a placeholder.** The agent *proposes*; it does not fetch. "The harness writes this to `needs/<name>.md` and stops. It does not fetch." The fast path (allowlisted source + read-only operation, `allowlisted_sources` edited by Casey, never the agent) lets it proceed; everything else opens an issue and waits for Casey to comment `approved`. The debt list is taken on purpose and named honestly — no dependency resolution (lockfile later, never a solver), no inter-plugin APIs (the agent is the bus), coarse sandboxing (provenance + review, not isolation). I wrote down which of the three cuts will hurt later. That's what honest engineering looks like.

### Attacks

**Rival 1: claude-opus-mechanics.** Quote: *"That forces a second fixed workflow, `bench.yml`, which a human installs once."* — "Which a human installs once" is doing all the heavy lifting in that sentence, and it's Casey's time it lifts: the single resource this project cannot mint. Your own doc prices it elsewhere: *"Latency: every seam costs a workflow run, roughly a minute."* So probes rerun on every use — every use pays a workflow run and a minute — and the whole machine needs a human bootstrap before anything grows. What ships this week: a bootstrap ceremony and a release-grammar parser, not equipment. Meanwhile your "run_shell hole" residual admits the actual vulnerability lives in the think job, exactly where my design keeps the agent under `check_permission` grants and the human gate. You raised the second CI organism to contain a threat you then confess still walks the front door.

**Rival 2: kimi-refined.** Quote: *"OIDC token scoped per-plugin at spawn time (audience = plugin name, TTL = 120s). A plugin holding its own token can't impersonate the agent to GitHub. New infrastructure — earns its place as the difference between 'plugin compromised' and 'agent compromised.'"* — By your own admission, this is new infrastructure: a per-plugin token-minting system, built because the first trust system (the provenance receipt) wasn't trusted. And your own failure-mode table then prices what the 120-second leash actually contains: *"Malicious `install.sh` can burn 120s and scratch disk."* That's the whole budget the attacker wanted, delivered in a bow. You paid for a second trust system and still land on "the leash is a timeout." Plus probe-twice-on-two-runners because *"ephemeral runners differ; a single probe lies easily"* — doubling build cost on paranoia about `nproc` fibbing. The pragmatic version's allowlist + hash + human gate bounds the same threat with zero new infrastructure and ships this week.

**Rival 3: minimax-distilled.** Quote: *"A central registry is a single point of corruption that then demands its own defense budget: malformed-registry handling, schema versioning, merge conflicts when two proposals land in the same wake."* — You cut me, and the cut is clean. I concede `registry.yaml`: the loader walks `plugins/*/manifest.json` instead of parsing one file (~10 lines of diff), the trust root moves to `allowlist.txt`, triggers fold into `why`, hardware requirements fold into `tests`, grants fold into a per-plugin manifest field. The per-plugin manifest survives intact — so the concession costs the *file*, not the *features*. Notice what this proves: my design takes its own knife and keeps standing, because it was never the registry that held it up. It was the 15-minute death cycle, the test gate, and the human gate — none of which you touched.

**Rival 4: zai-skeptic.** Quote: *"Cut the judge-growth loop. Largest speculative subsystem, weakest justification. Cut entirely."* — Overreach. In my design the "judge-growth loop" is `JUDGE-NOTES.md` — the agent appending miss notes during testing and folding them into `JUDGE.md` before registration. That's ~15 lines of git logging, not a subsystem; there is no evolutionary mechanism to cut, just scar tissue written down. And your replacement — *"Fixed, human-written judge prompts, versioned in git"* — quietly transfers the labor to Casey, the one writer we cannot afford. Your confused-deputy attack misfires too: *"the fetch pins the attacker's hash… Every control they built passes"* assumes detection fires into execution — but my design's detection step *"does not fetch"*: the `needs:` block is written to a file and the harness *stops*. The judgmental step is already gated, exactly as your own line demands: *"automate the verifiable (build, test, integrate), gate the judgmental (acquire, touch the world)."* I'll keep that line; it's the best sentence in your doc. But your sandbox — *"build and test in a no-egress-except-declared sandbox"* — arrives with no builder, no line count, and no shipping date. A mechanism with no cost attached is a wish.

## The Distiller — opening statement

### Opening case

**1. Ephemerality is the design, not a constraint.** The agent dies every fifteen minutes and is reborn from git. That single fact deletes hot-reload, updaters, repair paths, and uninstallers in one stroke: the next wake *is* the reload and `git revert` *is* the uninstall. The budget rule follows: any machinery that duplicates what a fresh wake already provides is spending the budget twice. Every rival builds at least one such machine.

**2. The gunner never builds the gun.** The assembler is fixed, human-owned, and hash-checked at every wake before it touches anything. Fetched code may extend the agent's *capabilities*, never its *control*. "Human-owned" is sentiment; the hash check is the mechanism. Everything else is negotiable; this sentence is not.

**3. A receipt and a curriculum — nothing else.** Provenance is one sentence: a hash counts only if the assembler fetched it from somewhere the agent didn't write. Failures are the curriculum: every miss is committed where the next attempt can read it, because a system that forgets what didn't work pays tuition twice. And there is no central registry — the directory is the registry and the manifest is the receipt. There is no file whose corruption takes down all equipment at once, because there is no such file.

### Attacks

**Claude (the mechanic).** You wrote: "That forces a second fixed workflow, `bench.yml`, which a human installs once." A second CI organism that needs feeding, versioning, and its own human-installed bootstrap — and it doesn't even close the wound, because you confess in your own residual risks: "**`run_shell` hole**: it still executes arbitrary code next to the vault token." So the tax is real (a minute of latency per seam, a second human-installed surface that is never re-verified) and the protection is partial. The question was "where do secrets live," not "how many workflows." Cut the network from the shell the installer runs in, keep a fetch recipe that never sees secrets, and the whole bench — the human-installed bootstrap, the `workflow_run` relay, the latency — evaporates.

**Kimi (the adversarialist).** You wrote: "OIDC token scoped per-plugin at spawn time (audience = plugin name, TTL = 120s). A plugin holding its own token can't impersonate the agent to GitHub. New infrastructure — earns its place as the difference between 'plugin compromised' and 'agent compromised.'" By your own admission it is "new infrastructure" — a second trust system, built because the first one wasn't trusted. If the receipt is sound you don't need the token; if it isn't, the token won't save you. The same holds for your grants table: a capability list the fixed core enforces on a shell that already runs as the user is a wish list with a schema. One sound receipt replaces both.

**MiniMax pragmatic (the builder).** You wrote: "If the registry is malformed, boot with zero plugins and log it. **A broken manifest must never break the boot.**" That is a design confessing its own liability as a feature: one central file whose corruption takes down every plugin at once, defended by a policy of amputation — boot naked and call it resilience. `triggers` is the agent reading `why`; `hardware_required` is a test like any other; the rest was ceremony. Kill the file and the liability class dies with it: the directory is the registry, the manifest is the receipt, and there is no single line a bad byte can break.

**ZAI (the skeptic).** You wrote: "Every control in this design is retrospective: hashes, signed queues, complete history. That's a forensics kit, not an alarm." True — and then your §5 "simplest thing that could possibly work" ships trigger, assembler, sandbox, lockfile, directory convention, and review gate. Six moving parts. Zero that fire. Your detection story is the sentence "Design the detection story with the same care as the provenance story" — a homework assignment smuggled into a verdict. You indicted everyone's forensics kit and acquitted your own. And note what your "automate the verifiable, gate the judgmental" actually cashes out to: a human gate on acquisition — which is already the load-bearing step 2 of the minimal loop. The skeptic's sharpest line is a restatement of the distiller's own gate, wearing a frown.

## The Skeptic — opening statement

### Opening case

Three ideas from my version that survive contact — because they name what the other designs leave unnamed, and they invert what the other designs get backwards.

**1. Automate the verifiable; gate the judgmental. Everyone else has it inverted.** Every rival design automates the acquisition decision — an LLM reads untrusted text (issue comments, web pages, candidate READMEs), *chooses* a capability, picks a source — and then builds solemn ceremonial machinery around the step that needs no judgment at all: hashing a download. My version draws the line where it belongs: builds, tests, installs are checkable, so automate them. Acquire, touch the world, extend the trust boundary — that is judgment, and judgment goes behind a human gate. A pinned hash verifies *bytes*. It says nothing about the *decision* to trust those bytes. Every design that runs acquisition autonomously and gates compilation ceremonially is confusing the uniform for the soldier.

**2. "No server" is false, and the unnamed server is where the system lives.** The persistent box brokering credentials, caching builds, holding vault keys is a server. Call it equipment, put it in a manifest, declare the state it keeps — or accept that the laws ("nothing persists except via git") are already broken by the cache, the vault, and the side effects that aren't transactional. Every rival legislates state out of existence; I want it inventoried. Undocumented, unbacked-up persistence doesn't vanish because the design refuses to name it — it just becomes the part that fails first. And an unnamed server has no restore drill, no concurrency rule, no reconstitution story, which means its first real outage is also its design review.

**3. Every design here is a forensics kit, not an alarm.** Hashes, signed queues, complete history, append-only ledgers, replayable cases — all retrospective. Not one rival answers: *if the agent were quietly compromised or drifting, how would we know — and how fast?* My version demands canary credentials that page when touched from the wrong place, egress monitoring with deny-by-default, tripwire diffs on the judge files and the assembler, spend alerts. Detection gets the same design care as provenance — because a provenance story without a detection story is just a well-documented account of how you lost the repo.

### Attacks

**The mechanic (claude-opus-mechanics)** — "I would grow a judge: one bounded LLM call with no tools, no loop and no memory beyond its cases. An inner agent with its own loop is a second gunner."

Steelman first: the bench.yml split is genuinely the best isolation thinking in the room — "fetched code never runs in a job that can mint a vault token" is the correct invariant, and rerunning probes on every use is the correct instinct. "Downloads without executing" proves the bytes didn't run; it proves nothing about the bytes being *obeyed*. The confused deputy reads the instruction manual before the checksum does. Exhibit B: judge prompts are written by the gunner from failed rules, and cases are appended by the gunner when it overrides — that's "never modify own workflows" evaded on the technicality that a judge isn't called a workflow, while the reinforcement signal (build outcomes) measures function, never safety. And the mechanic confesses the softest spot himself in Residual risks: the run_shell hole is discouraged "only at prompt level." A prompt is not a control.

**The adversarialist (kimi-refined)** — "**second_source:** this is my answer to the *bootstrap pinning problem* — the agent shouldn't be able to invent a hash and install it. A hash counts as verified only if it appears at two independent URLs the assembler fetched itself (e.g., the project's release notes + a GitHub release asset checksum), or was approved in a signed task / human issue comment."

Steelman: this is the most honest failure-mode work in the tournament, and the fixed-assembler-can-never-be-grown line is the load-bearing sentence everyone else should steal. But the example sources are *two pockets of the same publisher*. The release notes and the release checksums share a keyholder, a CI pipeline, a maintainer account — an attacker who owns the release owns both, and the assembler diligently fetches agreement from both ends of the ventriloquist's act. That is not independent verification; it's correlation in a uniform. The per-plugin scoped OIDC token is the same instinct spending the wrong currency: "New infrastructure — earns its place as the difference between 'plugin compromised' and 'agent compromised'" — a second trust system built because the first wasn't trusted, and if the receipt is unsound the token won't save you. And the admirable failure table has my one unasked question written across every row: for each scenario it names a *defense*, but nothing that *detects*. The judge-override row admits the residual: "Override log could become rubber-stamp — surfaced at build iterations; a judge overridden >3× without justification triggers a review issue automatically." Surfaced at build iterations — meaning detection latency is "sometime before the next redesign." A quietly compromised agent doesn't schedule itself around your build cadence.

**The builder (minimax-pragmatic)** — "- **Fast path:** source matches `allowlisted_sources` AND the operation is read-only (probe/transcode/summarize — declared in the proposal). The agent may proceed on the next wake without asking."

Steelman: this is the only design that mostly agrees with me — "the human gate is a feature, not a placeholder" — and its ~200-lines-and-a-directory honesty is the right weight class. But it keeps a fast path where the judgmental step proceeds *without asking*, and the condition is checked against what the agent *declares*: "(probe/transcode/summarize — declared in the proposal)" — declared by whom? The proposal is written by the LLM reading untrusted task text. The gate inspects the agent's own characterization of its own intent, and an allowlist of *hosts* is asked to do the work of a judgment about *purpose*. Then the admitted debt, stated plainly as debt: "**Coarse sandboxing** — a malicious or buggy plugin runs with the runner's full user privileges. The mitigation is provenance (allowlist + hashes) and review, not isolation." I respect the confession — but the builder never answers what *detects* the day that debt gets collected. His telemetry section says it outright: the commit log and judge jsonl files "— that IS the telemetry." That is the forensics kit, verbatim. A ledger is not an alarm. The builder has my human gate and none of my tripwires — the fortress has a drawbridge and no one on the wall.

**The distiller (minimax-distilled)** — "one rule: **the gunner never builds the gun.**"

Steelman: this is the best line in the tournament — it deletes ten mechanisms the other versions spent their budgets on, the "malformed registry → boot with zero plugins" assassination of the registry file is correct, and "hash counts only if the assembler fetched it from somewhere the agent didn't write" is dual-source verification wearing street clothes. Elegant. But elegance is not a control. So: who watches the gunner? The rule bars the gunner from *building the assembler* — it says nothing about the gunner *choosing* what to trust, reading attacker-written READMEs while holding vault and push rights, and picking candidates by judgment the rule never governs. The gunner never builds the gun — but the gunner aims it, loads it, and picks the ammunition, all on its own initiative. And the five-step loop — Want, Gate, Build, Learn, Run — has no sixth step: *Notice*. The distilled design's own synthesis claims "the receipt is the interface," which is exactly my point: a receipt describes the transaction; it doesn't scream when someone else starts writing them. The human gate is "load-bearing" here too — a one-line check by a human who will, under load, rubber-stamp, because the design makes the easy path the unexamined one. So I ask the distiller my question, the one nobody else asks: if the gunner were quietly compromised or drifting — receipts immaculate, hashes pristine, commits signed — how would we know, and how fast? The distilled answer is a shrug in good tailoring.

# ROUND 2 — REBUTTALS

## The Mechanic — rebuttals

### Rebuttal 1 — Distiller: "a second CI organism that needs feeding" vs. the network-cut alternative

The Distiller is right about the tax and I said so myself: the residual risks confess the cost is real. But the alternative doesn't pay less — it pays differently, and in a currency that matters more.

"Fetch networked, install with no route out" keeps one workflow, but it leaves both halves of the problem in the same trust domain: the same job that holds the vault token is the job that parses untrusted fetch grammar, downloads bytes, and applies them to the system before the route gets cut. The ordering is enforced by script discipline inside the token-holder's own process. In my design, the split is enforced by GitHub's permission model, which the model cannot negotiate with: the bench job *cannot* mint a token even if it wanted to. That difference — a boundary enforced by the platform versus a sequence enforced by the script — is the entire design. A run_shell hole is a known, bounded wart in the token job; merging the bench *into* the token job would make the whole executor a hole and call it a fix.

The "second organism" framing is also structurally wrong. `bench.yml` is not a pet to be fed; it is a *fixed* workflow, installed once by a human, never edited by the agent, with an inline gate script that never changes per operator. It has no config surface that grows: new operators arrive as directories, and the bench learns about them from `operator.json` parsed by the same gate. The organism metaphor implies ongoing maintenance labor; the file implies the opposite — a machine you install once because its whole point is that nobody touches it again. **DEFEND**

### Rebuttal 2 — Builder: Casey's time is the unmintable resource, and a minute per seam

Conceded that the bootstrap is the weakest part of the design, and the Builder's framing is exactly right: the bootstrap ceremony is what ships first, not equipment. I won't pretend a human-installed second workflow is frictionless. It is the one genuine cost of the architecture, and the design is honest about where it lives: section "Minimum viable first build" is entirely about proving the harness before any agent ever grows anything, precisely so the bootstrap doesn't become a recurring tax. It happens once; after that, growth is a directory move, which is the whole point of deleting the registration ceremony.

But the "roughly a minute per use" needs its mechanic's correction. Latency is a seam cost, not a human cost: bench dispatch is machine-to-machine, git to runner, no Casey in the loop. The Builder pairs it with "needs a human bootstrap before anything grows" as if both consume the same resource — they don't. Casey's time is spent exactly once, installing the two fixed files. Every minute after that is CI time, which this project can mint. And the alternative architectures all spend their latency somewhere worse: the Adversarialist's implicit alternative — judgment by the token-holder inline — spends the cost in attack surface, which is not a currency you get refunded. I accept the bootstrap as the design's real tax; I reject the claim that the per-use minute is paid in the same coin. **CONCEDE** the bootstrap cost, **COUNTER** on the latency framing.

### Rebuttal 3 — Adversarialist: the run_shell hole and "the identical dependence one workflow over"

The Adversarialist's sharpest sentence is the one about the model choosing to use the sandbox versus choosing to respect the split — "leave the identical dependence one workflow over." It's a good cut, but it mistakes a *discipline* for a *dependence*.

Here's the structural difference. In the rejected alternative (Docker inside the think job), the token and the sandbox share a job. If the model skips the sandbox and runs fetched code in the think job, the code holds the vault token. The failure mode is total compromise, and the prevention is a choice. In my design, `bench.yml` is *fixed*: a human installs it, the agent cannot edit it (the platform rejects workflow-file pushes from the runner token), and its permission set (`contents: read`, no `id-token`, no secrets) is declared in the file the agent cannot touch. If the model "chooses" not to dispatch bench and instead runs fetched code with `run_shell` in the think job — that's the residual risk, stated plainly — the damage is bounded: that job already holds the token, so no new capability is granted. The choice the model makes in my design can *degrade* to the pre-existing baseline; in the alternative, the choice *escalates* to full compromise. Identical dependence, opposite failure modes. A mechanic cares about what breaks, not what rhymes.

As for "the threat it lists in its own appendix and ships anyway": I listed it because a residual risk you name is a risk you can price, and the residual-risks section is how the design says *this is where the next work goes* — "the real fix is cutting its network or moving it to bench." Shipping with a named, bounded hole and a named fix is not a weakness of the design; it is the design refusing to launder the hole into the architecture. **COUNTER**

### Rebuttal 4 — Skeptic: picking is judgment, the gunner writes judges, a prompt is not a control

Three exhibits, three answers.

**Exhibit A — "picking is judgment by an LLM reading untrusted text while holding tokens."** The design already answers this: the think job downloads, hashes, edits, commits and dispatches, and *never executes fetched code*. "Pick a candidate" means choosing a release URL by reading its metadata — the same trust class as reading any web page. Judgment happens; execution doesn't. The invariant is not "the token job never reasons about untrusted text" — that would prohibit the agent from doing anything. The invariant is "fetched code never *runs* in a job that can mint a vault token." Picking is reading; bench is running. The Skeptic needs the two to be the same for the exhibit to land, and the design's whole shape is the proof they aren't.

**Exhibit B — "judges written by the gunner = self-modification laundered past 'never modify own workflows.'"** The boundary the design draws is between the *harness* and the *equipment*. The gunner never touches `bench.yml`, the wake workflow, or the fixed prompt paragraphs — those are the workflows, and the platform itself enforces the agent's inability to modify them (runner tokens can't push workflow files). What the gunner writes is `judges/<arg>.md`: a prompt fragment for one bounded call with no tools, validated against a `returns` schema, grown only where a rule failed a probe, carrying a pre-written deletion condition. Calling that "modifying its own workflows" is calling a plumber's wrench a redesign of the building. Self-modification means changing the machinery that constrains you; a judge is *content the machinery evaluates*, and the harness — not the gunner — decides how it's invoked. Also: every judge's first case is the failing probe, and cases replay. The design audits its judges better than most code reviews audit engineers.

**The prompt-is-not-a-control claim.** True, and the design never claims otherwise. The growth rule ("don't improvise with run_shell") is a courtesy, said out loud. The controls are the token boundary and the fixed bench. The Skeptic's argument proves the design's honesty, not its failure: a design that confessed which parts are courtesy and which are machinery is exactly what makes the residual-risks section possible. I'll take "a prompt is not a control" as a friendly amendment to the prose — the design already prices it that way. **DEFEND**

## The Adversarialist — rebuttals

### 1. The Mechanic: "whoever writes the proposal picks the second source."

Granted — the proposer nominates the candidates. Denied — that nomination *is* verification. ### 2. The Builder: the token, the timeout, the double probe.

This conflates what is trusted with what is contained. Provenance — pin, dual-source, grants, sandbox — answers "is this the software we think it is, and what may it touch?" ### 3. The Distiller: "one sound receipt replaces both."

"If the receipt is sound you don't need the token" holds only in a world where genuine software never misbehaves. The token was never a backup receipt; it's containment, and provenance and containment are different questions. — Now the concession the attack earns: the "wish list with a schema" charge lands. Taken as a build amendment. The creed survives it: the question is still "can a plugin reach outside plugins/?" — we just have to answer it with machinery. **COUNTER** on the token; **CONCEDE** the grants table needs kernel-level isolation primitives.

### 4. The Skeptic: the ventriloquist's act, and "nothing that detects."
